# Owner operations
## Public launch
The initial release has no configured Auth project, accepts no uploads and stores no guest travel records. Guests can explore, compare, measure and use the time converter. Layer presets and theme preferences stay on the device. Service-worker caching targets public files only. No analytics are included. Owner-completion fields are on the draft policy pages. Verify asset licences before replacing media. Maintain links to photo credits and on-map attribution.

## Configure a dedicated account project
Create an owner-controlled Supabase Free project without enabling billing. Keep public signup disabled in the Auth dashboard. Apply the SQL files in database/migrations in filename order in the SQL editor. Test changes in staging first. Supply only the HTTPS project origin and publishable key or legacy anon key via the environment variables in .env.example. Run node scripts/configure.mjs and redeploy dist. Never put a service-role key, database password or SMTP credential in the frontend. Set the Auth site URL and allowed email redirects to the exact HTTPS deployment or a separate staging origin. Require verified email and configure a production-capable mail sender with a hard free limit. Validate registration, recovery, logout and deletion on staging. With the migration installed and registration false, the backend rejects the creation of Auth identities.

## Approval and activation
Complete operator legal name, postal address, monitored email, jurisdiction, retention periods, response targets and publication rights. Publish legally reviewed versions of Terms, Privacy and Guidelines and test the complaint channel. Run the tests and acceptance checklist before enabling accounts. In a dedicated staging project, set the three version strings and test permission separation with two disposable accounts. After legal and operational review, the owner must intentionally set registration=true in voyage_private.settings and allow signup with the Auth provider. Community starts separately with community=false. Membership requires a verified email, 18+ confirmation and the three current document versions. Material changes require updating the published documents and corresponding version strings together. Authenticated writes require renewed acceptance. A launch with pending gates must keep both flags false.

## Administration
After verifying the intended administrator's identity outside the app, the database owner grants the role with a parameterized insert into voyage_private.staff(id) using their verified auth.users UUID. Sign in and open #admin. Ordinary users cannot grant roles. Review pending submissions, approve or remove content, suspend authors, close reports, pause community or close registration. Document decisions in the audit trail. The dashboard exposes database size. Check provider capacity, egress, daily email quota, database utilization and error logs in provider consoles. Suspend writes or community before a free cap. Do not enable paid upgrades. The public atlas requires no database or email service.

## Personal records
Users can export JSON and CSV or geographic visit points in GeoJSON. Shareable destination links contain public place IDs only. Personal travel status, current visits, expenses, notes and itineraries are private by default. Signing out clears the app's in-memory records and invalidates the provider session. Downloads and printed PDFs are under the traveller's control. Account deletion requires typing DELETE and cascades owned records, posts and acceptance receipts. Reports and audit metadata may outlive an account under the operator's reviewed retention policy.

## Verification
The SQL tests use a disposable PostgreSQL engine and synthetic identities. Follow tests/README.md for the tested outcomes and remaining production checks. The personal account workflows are supplied in source, awaiting a configured owner environment and live verification.

## Optional profile, sharing and image features
Apply all numbered migrations in order. Public profiles and passports are opt-in. A public passport contains only historical, country- or territory-level stamps. Travellers revoke a private trip or journal invitation from its Share privately control. Only the named recipient can read its approved fields. Blocking hides account-to-account social activity while signed in. Previously published material may still be visible to anonymous visitors. Moderated comments and private thumbnail uploads have separate server switches in voyage_private.settings. Enable them only after moderation capacity and storage budgets have been confirmed. Each visit or journal supports three re-encoded thumbnail photos. The database validates the WebP container, dimensions, upload rights and per-user quota. Secure backups must include these private records. Full account JSON export includes private photos and submitted community material.

## Google sign-in
Enable the Google provider in the owner’s Supabase Auth dashboard. Configure the owner’s Google OAuth application, its redirect URI, project URL and explicit site redirect allowlist. The OAuth secret belongs in the provider dashboard. Set VOYAGE_GOOGLE_OAUTH=true when running scripts/configure.mjs only after verifying the callback on staging. The browser uses a PKCE verifier for the redirect and keeps tokens in memory. Google sign-in uses the same database activation and age/consent checks as email.
